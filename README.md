# Telegram Analytics Pipeline

Автоматическая система аналитики Telegram-канала: сбор метрик каждые 6 часов без участия человека, включая временные срезы просмотров и историю оттока/притока подписчиков.

Живой продукт: работает в облаке с июня 2026 на канале [«Приватный эфир»](https://t.me/Private_ether).

![Дашборд](docs/dashboard.png)

## Проблема

Telegram отдаёт только текущее число просмотров поста - истории нет. Невозможно ответить на базовые продуктовые вопросы:

- Какой охват набирает пост за первые сутки? (скорость распространения контента)
- Общее число подписчиков стоит на месте - это стагнация или ротация «пришло 5 / ушло 5»? Первое - проблема привлечения, второе - удержания, и лечатся они противоположно.

Сторонние сервисы аналитики либо платные, либо не работают с малыми каналами. Ручной сбор требует заходить в статистику по расписанию - на практике не выполняется.

## Решение

Пайплайн: **Telethon → Python → Google Sheets → Looker Studio**, запуск по расписанию через **GitHub Actions** (каждые 6 часов, бесплатно, не зависит от включённого компьютера).

```
Telegram-канал
     |  Telethon (userbot-доступ: Bot API не отдаёт просмотры)
     v
stats.py ──────────────┐
     |                 |  GitHub Actions (cron, каждые 6 ч)
     v                 |  секреты - в GitHub Secrets
Google Sheets <────────┘
  ├─ Посты      (метрики по каждому посту + формулы)
  ├─ Срезы      (контрольные точки 6/24/72/168 ч)
  ├─ Динамика   (история подписчиков, append-only)
  ├─ Дашборд    (сводка внутри таблицы, legacy)
  └─ _Аудитория (скрытый служебный слепок ID)
     |
     v
Looker Studio (визуализация, фильтр по периоду)
```

## Ключевые механики

**Временные срезы просмотров.** Раз в 6 часов скрипт вычисляет возраст каждого поста и один раз фиксирует контрольные точки 6, 24, 72 и 168 часов. Для каждого живого замера сохраняются целевой и фактический возраст, точное время UTC, просмотры, реакции, пересылки, комментарии, ERR, Reach и число подписчиков. Из этих полей сразу считаются прирост, темп роста и просмотры в час.

Старые значения колонок «Просм. 24ч» и «Просм. 72ч» переносятся в `Срезы` с источником `legacy_posts`. Неизвестные время замера, фактический возраст и исторические реакции остаются пустыми: система не дорисовывает прошлое. Новые точные точки имеют источник `live`. Пара `(ID поста, целевой час)` уникальна, поэтому повторный запуск не создаёт дубли.

Колонки 24ч/72ч в листе `Посты` сохранены для обратной совместимости с существующими отчётами. Нормализованный лист `Срезы` предназначен для новой аналитики и Looker Studio:

- сравнение скорости набора просмотров на 6/24/72/168 часах;
- прирост между соседними контрольными точками;
- динамика ERR и Reach в течение недели после публикации;
- сравнение постов одного возраста без перекоса в пользу старых публикаций;
- поиск постов с быстрым стартом или длинным «хвостом» просмотров.

**Отток и приток подписчиков.** Скрипт хранит слепок Telegram ID аудитории и на каждом запуске сравнивает с прошлым: новые ID - «пришло», исчезнувшие - «ушло». Частичный результат Telegram отбрасывается, а строка истории и новый снимок записываются одной атомарной операцией. Хранятся только псевдонимные числовые ID, без имён и username.

**Отказоустойчивость.** Старые посты и ручные значения объединяются со свежими данными без предварительной очистки листа; части медиальбомов собираются в один логический пост; срезы идемпотентны; шапки самовосстанавливаются; неполный снимок аудитории не меняет историю; формулы учитывают локаль таблицы.

**Минимальные права Google.** Таблица открывается напрямую по `SPREADSHEET_ID`, поэтому сервисному аккаунту выдаётся только область доступа Google Sheets. Общий доступ ко всему Google Drive приложению не требуется.

## Дашборд

Данные из Google Таблицы визуализируются в Looker Studio: KPI-карточки, динамика подписчиков, приход/уход, топ постов по просмотрам, просмотры по датам, фильтр по произвольному периоду. Тёмная тема, один акцентный цвет.

Обновление: сбор данных каждые 6 часов → таблица → кэш Looker. Ссылка на живой дашборд не публикуется: статистика канала остаётся приватной.

### Как использовать `Срезы` в Looker Studio

Лист подключается отдельным источником с диапазоном `Срезы!A:R`. Даты поста и замера задаются типом Date & Time, целевой час — измерением, остальные числовые поля — метриками.

| Задача | Измерение/фильтр | Метрика |
|---|---|---|
| Сравнить просмотры постов одного возраста | `Цель, ч` или фильтр на 24/72/168 | `AVG(Просмотры)` |
| Показать траекторию отдельного поста | `Цель, ч`, разбивка по `ID поста` | `Просмотры` |
| Оценить длинный хвост | фильтр `Цель, ч = 168` | `Прирост просмотров`, `Прирост %` |
| Сравнить скорость старта | фильтр `Цель, ч = 6` и `Источник = live` | `Просмотров/час` |
| Взвешенный ERR по группе | `Источник = live` | `(SUM(Реакции)+SUM(Пересылки)+SUM(Комментарии))/SUM(Просмотры)*100` |
| Взвешенный Reach по группе | нужный контрольный час | `SUM(Просмотры)/SUM(Подписчики при публикации)*100` |

`legacy_posts` можно использовать для просмотров, Reach и прироста 24→72 часа. Для анализа фактического возраста, скорости и ERR нужен фильтр `Источник = live`, потому что старые исходные данные этих значений не содержали. Число постов считается как `COUNT_DISTINCT(ID поста)` или при фиксированном контрольном часе: обычный `COUNT` без фильтра посчитает один пост несколько раз. Текущее число подписчиков по-прежнему берётся из `Динамики`, а не из `Срезов`.

### Почему ERR — основная метрика

Система считает несколько метрик, но на основном дашборде использует ERR:

| Метрика | Формула | Использование |
|---|---|---|
| Реакции / просмотры | реакции / просмотры | Узкая оценка отклика |
| Reach % | просмотры / подписчики при публикации | Анализ контрольных срезов, с осторожностью на малой базе |
| **ERR %** | (реакции + пересылки + комментарии) / просмотры | Основная метрика вовлечённости |

Причина - знаменатель. Метрики относительно подписчиков на старте канала легко получают огромные значения: математика верна, но сравнение постов искажается. ERR делится на просмотры и лучше подходит для сопоставления публикаций разных периодов. Reach остаётся в `Срезах` как диагностическая метрика вместе с размером аудитории и возрастом поста, а не как безусловный KPI.

**Вывод: метрика надёжна ровно настолько, насколько надёжен её знаменатель.** На дашборд вынесена только ERR. Метрики от подписчиков вернутся, когда база стабилизируется - подрисовывать их сейчас значило бы врать себе.

ERR полнее классического ER и по смыслу: пост, который пересылают, важнее поста, которому ставят лайк.

### Два источника подписчиков

Число подписчиков живёт в двух листах с разной логикой обновления:

- **Посты** - подписчики на момент выхода поста (обновляется по событию: вышел пост);
- **Динамика** - снимок каждые 6 часов (обновляется по расписанию).

Карточка «Подписчики» на дашборде читает из «Динамики». Если брать из «Постов», она замирает между публикациями и расходится с графиком: подписчик пришёл, «Динамика» это записала, а «Посты» - нет, потому что нового поста не было.

Одно и то же число в двух источниках с разными триггерами обновления - выбор правильного источника под конкретный вопрос решается на уровне модели данных, а не визуализации.

## Стек

Python (Telethon, gspread, gspread-formatting) · Google Sheets API (сервисный аккаунт с областью Sheets) · GitHub Actions (cron + secrets) · Looker Studio · UTC-нормализация дат

## Настройка

Зависимости устанавливаются из зафиксированного `requirements.txt`:

```bash
python -m pip install -r requirements.txt
python -m unittest discover -s tests -v
```

Для GitHub Actions требуются Secrets: `API_ID`, `API_HASH`, `CHANNEL`, `SESSION_STRING`, `GOOGLE_CREDENTIALS` и `SPREADSHEET_ID`. Для локального запуска используются переменные с теми же именами. `POST_FETCH_LIMIT=0` (значение по умолчанию) загружает всю историю; положительное значение ограничивает число свежих сообщений, при этом уже накопленные строки не удаляются.

## Продуктовые решения и trade-offs

| Решение | Альтернатива | Почему так |
|---|---|---|
| Точность срезов ±6 ч | Сервер 24/7 с точными отметками | Для трендов достаточно; стоимость решения - нулевая |
| Фактический возраст рядом с целевым | Выдать поздний замер ровно за 24/72 ч | Видна реальная точность каждого измерения |
| Append-only `Срезы` | Перезаписывать одно текущее значение | Можно анализировать скорость и траекторию роста |
| Google Sheets как хранилище | БД + BI | Стейкхолдер один, шарится ссылкой, порог входа нулевой |
| Looker Studio для визуализации | Yandex DataLens | Читает Google Sheets напрямую, без публикации данных в интернет |
| Пустая ячейка при упущенном окне | Записать текущие просмотры задним числом | Фальшивые данные хуже отсутствующих: ломают средние |
| ID-слепок аудитории | Логировать username ушедших | Приватность важнее детализации churn-анализа |
| Одна метрика вовлечённости (ERR) | Показать все три | Две сломанные метрики рядом с рабочей обесценивают дашборд |

## Планы

- Подключить `Срезы` отдельным источником Looker Studio
- Вернуть Reach на дашборд с фильтром по контрольному часу
- Дневная агрегация «Динамики» по мере роста данных
- Корреляция оттока с контентом (какие посты «выносят» подписчиков)
